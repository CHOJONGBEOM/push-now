# Blog Writing Rules

## Purpose
단순한 기술 나열이나 일기형 기록이 아니라, **"비즈니스 문제를 정의하고 기술로 집요하게 해결해 낸 1인 메이커의 의사결정 과정과 제품 철학"**을 기록한다. 

## Target Audience & Voice
1. **타겟 독자**: 일반 대중이 아닌 **포트폴리오 방문자(채용 담당자, 그로스/마케팅 리더, 엔지니어링 리드)**를 대상으로 한다.
   - 실무 마케터에게는 "내 문제를 정확히 이해하고 도구를 설계할 줄 아는 사람"이라는 인상을 준다.
   - 테크/인사 담당자에게는 "문제를 엔지니어링으로 끝까지 파고들어 제품으로 완성해 내는 1인 풀스택 역량"을 증명한다.
2. **화자(Voice)**: 1인 개발 프로젝트이므로 주어는 무조건 **1인칭('나 / 저')**으로 일관되게 서술한다.
3. **적절한 분량과 압축성**: 백과사전식으로 모든 코드를 나열하거나 지나치게 방대할 필요가 없다. 핵심 병목, 기술적 판단 이유(Trade-off), 프로덕트 임팩트 중심으로 간결하고 흡인력 있게 전달한다.

## Absolute Rules
1. 실제로 하지 않은 경험, 실험, 실패, 수치, 성능 결과를 지어내지 않는다.
2. 정보가 부족하면 추측하지 않고 명확한 사실만 적는다.
3. 처음부터 정답을 알고 있었던 것처럼 포장하지 않는다.
4. 기술 스택을 단순 나열하지 않고, 도입 이유와 해결하려던 문제를 명시한다.
5. 작위적인 실패 서사를 억지로 만들지 않는다. (실패가 없었던 정석적 설계는 '요구사항 → 대안 비교 → 선택 이유'로 기술한다.)
6. 1인 운영 시 마주친 실제 복병(Doze 모드, 중복 수집, 법적 규제 등)과 해결책은 솔직하게 기술한다.
7. 독자(채용자/동료)가 쉽게 맥락을 잡을 수 있도록 핵심 용어와 데이터 환경을 친절하게 설명한다.
8. 과장된 마케팅 미사여구(Anti-AI Rules 준수)를 철저히 배제한다.

## Article Philosophy & Narrative Patterns
본문의 섹션 성격에 따라 다음 두 가지 서사 패턴 중 적합한 것을 선택한다.

### 패턴 A. 문제 해결 / 디버깅 서사 (시행착오가 있었을 때)
`문제 인식 → 현상 및 원인 분석 → 첫 가설/시도 → 예상 밖 복병 → 최종 해결책 → 배운 점 / 인사이트`

### 패턴 B. 아키텍처 / 기술 선정 서사 (정석적 설계 및 도입 시)
`비즈니스 요구사항 → 고려한 대안들(Trade-off 비교) → 해당 기술/구조를 선택한 이유 → 1인 운영 최적화 결과`

## Headings & Subheadings
기술명 명사 나열보다 **실제 부딪힌 문제와 의사결정을 담은 능동적인 제목**을 권장한다.
- ❌ 피해야 할 예: `"Redis 캐싱 적용"`, `"DB 설계"`, `"Timing 알고리즘"`
- ⭕ 권장하는 예: `"단순 정렬했더니 새벽 3시를 추천했다: 3중 가중치 기반 Golden Hour 알고리즘"`, `"마케터의 시선으로 설계한 스키마: 원본 알림에서 심리 트리거 추출까지"`

## Code & Implementation
1. 전체 코드를 무분별하게 복사하지 않고, **의사결정이 담긴 핵심 로직(10~30줄 내외)**만 보여준다.
2. 코드 상단에 파일 경로(`// src/hooks/useTimingData.ts` 등)를 주석으로 명시한다.
3. 변수명, 인터페이스, 핵심 수식 주석을 통해 코드를 읽는 것만으로도 설계 의도가 보이게 한다.

## Data and Evidence
실제 수치, 운영 로그, 쿼리 플랜, 테스트 결과, 스크린샷, 전후 비교(Before/After)를 적극 활용한다.
- 수치 표기 예: *“19,000+건 수집 데이터”, “가중치 65% / 25% / 15% 튜닝”, “Jaccard 유사도 70% 가드레일”*

## Anti-AI Writing Guide
다음과 같은 AI 특유의 상투적이고 공허한 표현을 엄격히 금지한다:
- `이번 글에서는 ~에 대해 알아보겠습니다.`
- `결론적으로 매우 성공적이었습니다.`
- `놀랍게도`, `눈부신`, `혁신적인`, `획기적인`, `완벽한`, `손쉽게`
- `단순히 ~를 넘어 A뿐만 아니라 B까지`
- `~의 새로운 지평을 열었습니다.`
추상적인 자화자찬보다 **구체적인 팩트와 고민의 흔적**을 담는다.

## Final Checklist
- [ ] 채용 담당자 / 마케팅 리더가 읽었을 때 프로젝트의 비즈니스 가치와 엔지니어링 역량이 와닿는가?
- [ ] 주어가 1인칭으로 일관성 있게 유지되는가?
- [ ] 분량이 불필요하게 늘어지지 않고 핵심 문제와 해결책 위주로 압축되었는가?
- [ ] 억지 실패 서사 없이 솔직하고 타당한 기술 선택 이유가 적혀 있는가?
- [ ] 수치와 지표에 명확한 근거가 있는가?
- [ ] AI 특유의 미사여구가 제거되었는가?
