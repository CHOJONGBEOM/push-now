# Technical Blog Writer (Story & Portfolio)

## Goal
실제 프로젝트의 코드와 운영 데이터를 기반으로, **비즈니스 문제 정의부터 아키텍처 판단, 시행착오, 인터랙티브 체감 요소까지 1인 메이커의 역량이 돋보이는 고품질 기술 아티클**을 작성한다.

## Core Rules & Context Reference
작업 전 반드시 다음 규칙들을 참조한다:
1. `.agents/rules/blog-writing.md` (타겟: 채용자/마케터, 1인칭 주어, 작위적 실패 방지, 팩트 기반)
2. `.agents/rules/blog-design.md` (가독성 우선, 인터랙티브 위젯 권장, 본문 너비 680~760px, 모바일 폴백)

---

## 4-Step Core Workflow

### Phase 1 — 탐색 및 팩트 추출 (Inspect & Extract Facts)
- 프로젝트 코드베이스(`src/`, DB 스키마, 백엔드/클라우드 설정 등)와 기존 스토리 페이지를 탐색한다.
- 핵심 비즈니스 문제, 실제 데이터 규모(수치), 주요 기술 선택(Trade-off), 1인 운영 시 마주친 실제 복병(Doze 모드, 규제, 중복 제거 등) 팩트를 추출한다.
- *주의*: 사실이 불분명한 내용은 추측해서 지어내지 않는다.

### Phase 2 — 목차 및 서사 설계 (Outline & User Checkpoint) 🛑
- 백과사전식 기술 나열을 지양하고, **문제 해결 서사(패턴 A)**와 **기술 선택 서사(패턴 B)**를 적절히 배분하여 목차를 구성한다.
- 소제목은 실제 부딪힌 문제와 의사결정을 담은 능동형 문장으로 설계한다.
- **[User Checkpoint]**: 목차 초안(섹션별 핵심 메시지 + 도입할 인터랙티브 위젯 아이디어)을 사용자에게 공유하고 피드백/승인을 받는다.

### Phase 3 — 본문 작성 및 컴포넌트 결합 (Drafting & Interactive Widgets)
- **1인칭 주어('나 / 저')**로 일관되게 작성하며, 불필요하게 늘어지지 않도록 핵심 위주로 압축 서술한다.
- **인터랙티브 위젯 & 시각화 결합**:
  - 독자가 원리를 직접 체감할 수 있는 인터랙티브 컴포넌트(슬라이더, 계산기 등)
  - Before/After 대비 카드, PipelineBox 도식, 핵심 코드 스니펫(경로 주석 포함)
- **Anti-AI Writing**: 상투적인 찬사나 기계적인 번역투 표현을 완전히 제거한다.

### Phase 4 — 검증 및 반응형 QA (Verification & Polish)
- **팩트 검증**: 수치(예: 19,000건), 알고리즘 가중치(65/25/15%), 파일 경로, API 명칭의 정확도 확인
- **반응형 체크**: 데스크톱(Sticky TOC, 와이드 도식)과 모바일(1열 스택, 가로 스크롤 보호)에서의 완벽한 렌더링 확인
- **타겟 독자 점검**: 채용 담당자나 마케팅 리더가 보았을 때 문제 해결력과 프로덕트 오너십이 명확히 전달되는지 점검.

## When Improving Existing Story Post
1. 기존 원문의 팩트와 마케팅/엔지니어링 의도를 100% 보존한다.
2. 억지 구어체나 이모지 남발을 정돈하고, 프로페셔널한 1인 메이커의 깊이 있는 톤으로 가다듬는다.
3. 정적인 텍스트 섹션 중 인터랙티브 위젯으로 전환했을 때 독자 경험이 극대화되는 지점(예: Timing 가중치 공식)을 발굴하여 제안/구현한다.
